How Many Amazon Scraper API Credits Will Your Workflow Need?

How many monthly credits will your Amazon product checks use? Estimate from your active ASINs, refresh schedule, and each endpoint’s documented cost, then compare the result with current plan allowances.

November 25, 2026 9 min read Pangol Info Team

A product count is not a monthly usage estimate. If you are comparing Amazon data APIs or choosing a plan for price monitoring, start with the calls your workflow will actually make, apply the documented credit cost for each operation, and then compare the result with the current plan allowance. This gives you a workload estimate—not a promise of a fixed bill.

Count scheduled requests, not just ASINs

For a workflow that requests one JSON Product Detail result for each ASIN, the first-pass calculation is:

monthly credits = ASINs checked × checks per ASIN in the month × credits per request

The current Product Detail API reference specifies one credit per JSON request. So a 30-day planning month with 200 ASINs checked once per day is 200 × 30 × 1 = 6,000 credits. That is below the published 9,600-credit Starter allowance, before other calls or any workload growth. If the same workflow checks 2,000 ASINs daily, the arithmetic becomes 60,000 credits—exactly the published Professional allowance, leaving no room in that example for additional operations or a heavier month.

These are example workloads, not plan recommendations. Use your actual number of active ASINs, billing-cycle days, and schedule. A second daily refresh doubles the scheduled Product Detail volume; checking half the catalog every day does not. For a workflow that only runs on weekdays or uses a rolling queue, count the planned executions rather than multiplying by a generic “monthly requests” figure.

Apply the cost of each operation

Do not assume every API call costs one credit. The official billing overview shows why the operation matters: Product Detail JSON is 1 point per request, Delivery Time JSON is 2, Revenue Calculator JSON is 5, and Amazon Review API Reviews JSON is 5. Check each selected operation's reference for its exact rate and billing unit before multiplying.

Keep workloads separated by operation so a later product change is easy to recalculate:

monthly total = Σ (monthly requests for each operation × that operation's credits per request)

For example, if each of 200 products gets one detail request daily and one review request weekly, calculate the Product Detail and Review API lines separately with their own published rates; then add them. Do not treat a returned product or review as a request unless that endpoint's billing unit says so. Pagination, requested page count, format, and endpoint-specific rules can change the actual charge.

For a completed fetch, use the response's pointCost as the observed charge where the operation returns it. In asynchronous mode, the docs say credits are reserved on acceptance and settled on completion; a no-content failure releases the reservation, while a callback delivery failure after successful parsing does not refund the completed fetch. Those details matter when estimating retries and reconciling usage.

At one-credit Product Detail JSON calls, 60 Free credits correspond to 60 such requests in the cycle—not 60 products checked every day. The 6,000-credit example fits within Starter's listed allowance; the 60,000-credit example uses all of Professional's listed allowance. Whether either is a good fit depends on the rest of your workload, not just the example's arithmetic. Prices and terms can change, so refresh the calculator and account terms before choosing or paying.

Build a buffer from real work

A plan that only fits the average month may be too tight if you regularly backfill missed observations, add newly selected ASINs, run an extra marketplace, or fetch reviews as well as product details. Add those calls to the estimate explicitly. If the actual operation rate or request schedule is not known yet, run a small representative test and review the returned pointCost; do not invent a universal 10% or 20% buffer.

Keep peak and ordinary use separate. For example, a launch-week backfill can be listed as a second scenario beside the normal daily schedule. That makes it clear whether a higher allowance is needed every billing cycle, only for the launch, or not at all. The Amazon Scraper API page has the current product and pricing calculator; confirm the chosen operations and formats there rather than relying on an old spreadsheet's per-request assumption.

Check the billing boundary before you commit

The live pricing page describes the paid base plans as minimum monthly commitments and says usage above plan volume follows tiered usage pricing. It does not make the listed plan price a universal per-request rate. Compare the monthly allowance with the estimate, then use the current calculator and account terms to understand any usage beyond it; do not divide a subscription price by one endpoint's request count and apply that rate to a different API.

One detail deserves a direct account check: the base-plan help article says unused monthly credits expire at the end of the billing cycle and cannot carry over, while the live pricing FAQ says rollover follows the terms shown in the account. Until the account's current terms clarify which applies to your setup, do not budget on unused credits carrying forward.

For the separate question of whether price snapshots are still timely enough for a decision, see When Was This Data Observed?. This guide is about monthly usage planning; freshness, marketplace coverage, and actual API response fields still need their own checks.

A practical plan-fit checklist

  1. Write down the active ASIN count and the planned number of checks in one billing cycle.
  2. Split the calls by endpoint and format, then use each documented credit rate.
  3. Add expected backfills, extra marketplaces, and review or delivery operations as separate lines.
  4. Compare the ordinary and peak-month totals with the current plan allowance.
  5. Use the live pricing calculator and your account's current terms to review any over-plan usage, rollover, and final billing details.

Bottom line: estimate credits from scheduled operations, not catalog size alone. For one JSON Product Detail call per ASIN, per check, the unit cost is 1 credit; the example of 200 ASINs checked daily over 30 days totals 6,000 credits. Recalculate with your actual cadence and all endpoint types, then verify live terms before selecting a paid plan.
