Amazon Scraper API 每月要多少 Credits？按商品量与刷新频率估算

按追踪商品数、刷新频率和接口单次成本估算 Amazon Scraper API 月度 Credits，再与当前套餐额度和计费条款对照。

2026年11月25日 8 分钟阅读 Pangol Info Team

商品目录有多少条，并不等于每月 API 用量。若你正在比较 Amazon 数据 API，或要为价格监控选套餐，先列出工作流实际会发出的请求，按每种操作的文档成本计算，再与当前套餐额度对照。这样得到的是工作量估算，不是固定账单承诺。

数计划执行的请求，而不只是 ASIN

如果工作流对每个 ASIN 发起一次 JSON 商品详情请求，第一步可以这样算：

月度 Credits = 检查的 ASIN 数 × 每个 ASIN 当月检查次数 × 每次请求 Credits

当前商品详情 API 文档规定，JSON 请求每次消耗 1 credit。以 30 天为一个规划月，200 个 ASIN 每天检查一次，就是 200 × 30 × 1 = 6,000 credits。仅按这部分计算，低于当前公开的 Starter 9,600 credits；其他 API 请求和用量增长还没有计入。若每天检查 2,000 个 ASIN，则是 60,000 credits，正好等于当前公开的 Professional 月度额度；这个例子里没有给额外操作或更忙的月份留空间。

这些只是工作量示例，不是套餐推荐。请使用实际活跃 ASIN 数、账期天数和执行计划。每天多刷新一次，商品详情请求量就会再增加一轮；若每天只检查一半目录，也不应按全量目录估算。若工作流只在工作日运行，或使用滚动队列，就按计划实际执行的次数计数，而不是套用一个笼统的“月请求量”。

按每种操作分别套用计费规则

不要假设所有 API 调用都只花 1 credit。官方计费概览说明不同操作的成本可能不同：商品详情 JSON 每次请求 1 点；配送时间 JSON 为 2 点；收入计算器 JSON 为 5 点；Amazon Review API 的 Reviews JSON 为 5 点。计算前应查看所选操作文档中的确切费率和计费单位。

把不同接口的用量分开记，之后改工作流时才容易重算：

月度总量 = Σ（每种操作的月请求数 × 该操作每次请求的 Credits）

例如，对 200 个商品每天各发一次详情请求，再每周各取一次评论，就应分别按商品详情和 Review API 的公开费率计算，再把两行加起来。除非某个接口明确按返回条目计费，否则不要把“返回的商品数”或“评论数”当成请求数。分页、请求页数、格式及接口特定规则都可能改变实际费用。

接口返回实际计费字段时，可用完成请求的 pointCost 记录已发生的费用。异步模式下，文档说明系统接收请求时先预留 Credits，完成后再结算；没有内容的失败会释放预留额度，而解析成功后的回调投递失败不会退回已完成请求的费用。这些规则会影响重试与用量核对。

按每次 1 credit 的商品详情 JSON 请求计算，Free 的 60 credits 在一个账期内只对应 60 次这类请求，不是每天检查 60 个商品。6,000-credit 示例落在 Starter 的公开额度之内；60,000-credit 示例用完了 Professional 的公开额度。是否合适还要看示例以外的调用，不只看这一步乘法。价格和条款可能变化，选择或付款前请重新查看计价器和账户条款。

用真实工作量留出余量

只覆盖普通月份平均值的套餐，在补抓漏掉的观测、新增待追踪 ASIN、扩展到另一个市场站点，或同时抓评论时可能不够。把这些请求明确加到估算里。如果实际接口费率或执行频率还不清楚，先用代表性的小样本测试并检查实际返回的 pointCost；不要凭空设定一个普遍适用的 10% 或 20% 余量。

把高峰用量和普通用量分开。例如，新品发布周的历史回填可以作为单独情景，与常规每日任务并列。这样才能判断要不要每个账期都买更高额度、只在发布期增加用量，还是当前工作量已经足够。Amazon Scraper API 产品页提供当前产品和计价器；要核对实际操作与格式，请以实时计价工具为准，不要沿用旧表格里“每次都一样”的假设。

购买前确认账期边界

当前计价页把 Starter、Professional 和 Expert 描述为最低月度承诺，并说明超出套餐用量后会按阶梯用量计价；套餐月价并不是适用于所有接口的统一单次请求费。先将月度额度与估算量比较，再用实时计价器和账户条款了解超额用量；不要把订阅价格除以某个接口的请求数，再把该费率套到其他 API 上。

有一项最好直接在账户中核对：基础套餐帮助文档称未使用的月度 Credits 会在账期结束时失效、不能结转；但当前计价页 FAQ 表示结转规则以账户中显示的条款为准。在账户条款明确适用于你当前设置之前，不要把未用 Credits 计入下个账期预算。

如果你还需要判断价格快照是否足够新、能否支撑决策，可读《API 数据何时被观察？》。本文只解决月度用量规划；数据时效、市场覆盖和实际响应字段还要分别核验。

套餐匹配核对清单

  1. 写下活跃 ASIN 数，以及一个账期内计划检查的次数。
  2. 按接口和输出格式拆分请求，再套用各自文档中的 Credits 费率。
  3. 把回填、额外市场站点，以及评论或配送等操作单列进去。
  4. 将普通月份和高峰月份分别与当前套餐额度比较。
  5. 用实时计价器与账户条款确认超额用量、结转和最终计费细节。

结论：按计划执行的操作估算 Credits，不要只看目录里有多少商品。单次 JSON 商品详情请求按 1 credit 计算；例如 200 个 ASIN 每天检查一次、按 30 天规划，就是 6,000 credits。再按你的真实频率和全部接口重算，最后核对实时条款后再选付费套餐。

200 个 ASIN 每月要多少 Credits？如果每个 ASIN 每天发一次商品详情 JSON 请求，按 30 天规划为 6,000 credits；其他接口和临时调用不包含在内。

每天检查 2,000 个 ASIN 用哪个套餐？同样按每个 ASIN 每天一次、30 天计算，共 60,000 credits，正好等于当前公开的 Professional 月额度。这个估算没有额外请求余量，购买前请纳入完整工作流并确认当前计费条款。

一个 credit 就等于一次请求吗？并非所有 API 都如此。商品详情 JSON 当前列为每次请求 1 credit；其他接口有各自的费用和计费单位。请查看具体操作文档与实际返回的 pointCost。
