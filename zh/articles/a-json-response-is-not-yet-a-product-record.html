JSON 响应还不是商品记录：API 响应校验实践

在智能体或应用依据 API 数据作出决策前，先验证响应结构、字段与缺失值。

2026年11月23日 12 分钟阅读 Pangol Info Team

一次 HTTP 请求成功、JSON 语法有效，只是可靠数据流程的起点。在智能体比较商品或建议行动之前，客户端必须确认响应结构符合预期、每一行数据都可用，并让缺失值继续保持缺失，而不是悄悄把它转换成确定结论。

这一区别很重要，因为应用常常只用一行代码就把嵌套响应变成业务决策：results[0].price。如果包装结构、解析器或单条记录与代码预期不同，这个捷径可能直接报错；更糟的是，它也可能产出看似合理、实际错误的答案。

当前 Pangolinfo Amazon Scraper API 示例展示了嵌套在 data.json[0].data.results 下的结构化结果。这是一个可供适配的响应约定，并不意味着每个解析器、输出格式或未来响应都会采用完全相同的结构。

在 JSON 与应用之间建立边界

在响应体通过一个小型适配器之前，把它视为 unknown。以下三个问题应分别判断：

  1. 请求是否到达 API，并收到了 HTTP 响应？
  2. API 是否报告操作成功，且响应信封结构符合预期？
  3. 每条返回记录是否包含当前应用实际需要的字段？

这代表不同的结果。HTTP 错误不等于搜索结果为空；API 层错误不等于成功响应但结果数为零；包含空 results 数组的有效信封，也不等于格式错误的响应。应为每种状态单独定义结果，让下游代码能够准确处理。

下面是针对文档所示嵌套响应的刻意精简 TypeScript 示例。它用于说明边界，并非生成的 SDK，也不是适用于所有解析器和输出格式的通用解码器。

type JsonObject = Record<string, unknown>;

type DecodeResult =
  | { kind: "ok"; rows: unknown[] }
  | { kind: "empty" }
  | { kind: "api_error"; code: unknown; message?: string }
  | { kind: "invalid_shape"; at: string };

function object(value: unknown): JsonObject | undefined {
  return value !== null && typeof value === "object" && !Array.isArray(value)
    ? value as JsonObject
    : undefined;
}

function decodeDocumentedEnvelope(payload: unknown): DecodeResult {
  const root = object(payload);
  if (!root) return { kind: "invalid_shape", at: "root" };

  if (typeof root.code !== "number") {
    return { kind: "invalid_shape", at: "code" };
  }
  if (root.code !== 0) {
    return {
      kind: "api_error",
      code: root.code,
      message: typeof root.message === "string" ? root.message : undefined,
    };
  }

  const data = object(root.data);
  const pages = data?.json;
  if (!Array.isArray(pages) || pages.length === 0) {
    return { kind: "invalid_shape", at: "data.json" };
  }

  const first = object(pages[0]);
  const inner = object(first?.data);
  const rows = inner?.results;
  if (!Array.isArray(rows)) {
    return { kind: "invalid_shape", at: "data.json[0].data.results" };
  }

  return rows.length === 0 ? { kind: "empty" } : { kind: "ok", rows };
}

这样的适配器能让失败位置明确。在生产环境中，应依据实际调用的具体操作和输出格式定义解码逻辑，并将传输错误与已解码的 API 结果分开表示。

校验决策实际依赖的字段

结果行即使是对象，也未必包含应用想要的所有字段。应校验当前任务所需的最低契约，而不是想象一个适用于所有场景的通用商品结构。

例如，在关键词搜索流程中，去重前可能必须有可用的商品标识符；如果后续步骤不依赖标题、价格、排名或图片，这些字段可以是可选项。在价格比较中，价格字符串可能是必需的，但应用仍应保留原始文本，不能把缺失价格解释成零。

type ProductRow = {
  asin: string;
  title?: string;
  price?: string;
};

type RowCheck =
  | { kind: "usable"; product: ProductRow }
  | { kind: "rejected"; reason: string };

function validateProductRow(value: unknown): RowCheck {
  const row = object(value);
  if (!row) return { kind: "rejected", reason: "row_not_object" };
  if (typeof row.asin !== "string" || row.asin.trim() === "") {
    return { kind: "rejected", reason: "missing_asin" };
  }

  return {
    kind: "usable",
    product: {
      asin: row.asin,
      ...(typeof row.title === "string" ? { title: row.title } : {}),
      ...(typeof row.price === "string" ? { price: row.price } : {}),
    },
  };
}

这是有意采取的保守做法：示例不会把价格解析成数字，不会声称得出了含运费总价，也不会编造缺失的标题。只有当业务任务已定义币种、地区格式和报价语义时，才应在另一个经过测试的领域层中规范化价格。

单条记录出错时保留可用记录

一条格式错误的记录不必抹掉其余有用结果。应逐行校验，保留可用记录，并按原因计数或记录被拒绝的行。这样，调用方才能选择合适的处理方式：用较小的数据集继续、在理由充分时重试特定请求，或在证据不足时请人工审核。

不要悄悄丢弃完整的错误上下文。一个有用的内部结果可以同时携带 usableProducts 和 rejectedRows，以及生成这些记录的请求上下文。面向用户的答案应只基于可用证据；如果被拒绝的部分可能改变结论，就应说明这一限制。

将请求上下文与记录一并保存

如果没有请求上下文，之后就很难解释一条商品记录。应将定义本次请求的输入与采集记录一起保存，例如解析器、市场站点、请求内容或目标标识符、输出格式，以及任何配送地点上下文。不要把凭证写入日志。

把系统自己的 received_at 时间戳记录为系统收到响应的时间。除非 API 明确提供源页面时间戳，否则不要把它重新标注成源页面被观察到的时间。调试监控或解释两次运行为何不同，这一区分尤其有用。

用固定测试样例检验边界

与只覆盖成功路径相比，一组小型固定测试样例能发现更多脆弱的客户端问题。测试至少应包括：

  • 包含一条有效记录的文档示例成功信封；
  • 非成功的 API code；
  • 结果数组为空但结构有效的信封；
  • 缺少 results 字段，或该字段类型错误；
  • 缺少当前工作流所需标识符的记录；
  • 有效记录缺少可选字段。

针对每个样例，都要断言结果类别及下游行为，而不仅仅确认 JSON.parse 没有抛出异常。结构变化应表现为清晰可见的适配器错误，而不是基于默认值生成的商品建议。

把不确定性作为一等结果

目标不是拒绝每一个不完整响应，而是让其边界清楚可见。客户端可以返回可用记录，同时指出所需字段缺失；也可以报告结果为空，但不因此断言商品不存在；如果价格比较所必需的价格不可用，也可以停止比较。

传输层 JSON 与应用数据之间的这道小边界，正是 API 集成建立可信度的地方。请查看所选操作在 Amazon Scraper API 参考文档中的响应契约，只校验当前决策真正需要的内容，并让不确定性一路保留到最终答案。
