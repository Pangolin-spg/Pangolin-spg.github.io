API 数据何时被观察？时间戳与数据时效边界

一次抓取结果不是“现在”的同义词。价格、库存和配送信息都带着一个隐含时间边界：它们说明系统在某次请求中取回了什么，却不能保证用户稍后看到的页面、下单时的报价或最终可购买状态仍然相同。把结果当作有上下文的快照，而不是永不过期的商品事实，能让监控、比较和自动化决策更诚实。

一次抓取结果不是“现在”的同义词。价格、库存和配送信息都带着一个隐含时间边界：它们说明系统在某次请求中取回了什么，却不能保证用户稍后看到的页面、下单时的报价或最终可购买状态仍然相同。把结果当作有上下文的快照，而不是永不过期的商品事实，能让监控、比较和自动化决策更诚实。

价格与库存不是静态属性

商品详情 API 可以返回 price、inStock、seller、shipper 和 delivery 等字段；配送信息也可能包含标准或最快配送时间。字段存在，不等于该值永久有效。一个页面上看到的价格可能与不同卖家、商品变体、市场或配送条件有关；库存和配送承诺也可能变化。

在把两次结果比较之前，先确认它们描述的是同一个对象和配送上下文。若要让配送情境一致，应在请求中明确指定同一个、且符合该市场的邮编；Pangolinfo 文档说明，不指定 bizContext.zipcode 时，后台会随机选择邮编，因此不能假定两次请求的配送条件相同。保存请求中明确指定的邮编；不要假设商品详情响应会返回后台实际使用的邮编。还要保留 ASIN、市场站点、相关变体和请求时间。具体字段及参数以所选商品详情操作文档为准。

记录两个时钟，而不是伪造一个

一次数据流程至少有两个可观测的时刻：应用发出请求的 requested_at，以及应用收到结果的 received_at。两者适合解释排队、传输和系统处理过程，但都不等同于源页面被观察到的时间。

当前商品详情字段说明列出了价格、库存、卖家和配送等数据，却没有在该字段清单中定义每条记录的源观察时间。不要把本地的 received_at 改名为 observed_at，也不要从同步响应或异步回调到达时间推断源页面恰在那一刻被采集。若接口明确返回源时间戳，再按其定义保存；否则把它留空或标记为“未提供”。

{
  "request_context": {
    "asin": "<requested ASIN>",
    "site": "<marketplace>",
    "zipcode": "<requested zipcode, if any>"
  },
  "requested_at": "<client timestamp>",
  "received_at": "<client timestamp>",
  "source_observed_at": null,
  "source_timestamp_status": "not provided by the selected response contract"
}

这是应用自己的审计记录示意，不是 Pangolinfo API 响应样例。将请求上下文与记录一起保存，也能避免日后把某个邮编、市场或变体的结果套用到另一个情境。

异步完成时间也不是源时间

异步模式会先返回 taskId，在抓取和解析完成后再把结果发送到回调地址。于是至少还要分开记录提交与回调接收时间。回调的时间告诉你应用何时收到完成结果；它本身不说明 Amazon 页面在何时被观察，更不承诺价格或库存会在某个时长内保持不变。请按异步 API 文档中所选操作的具体参数和回调约定实现。

让“可用多久”由你的决策定义

不要为所有数据设一个看似精确、实则没有依据的全局保鲜期。为每种用途定义最大允许的应用持有时间，以及超时后的动作：提示数据需要更新、重新查询、降级为“上次观察到”，或交由人工确认。这个阈值是你的产品策略，不是 API 的新鲜度保证。

例如，历史图表可以展示多次采集值及各自的接收时间；一个即将执行的价格动作，则可以要求在动作前重新取回数据并再次确认关键字段。即使刚收到一个响应，也不要把它写成下单时的保证报价。新请求减少了应用持有旧数据的时间，但不等于锁定页面状态或保证后续交易结果。

对变化事件也要谨慎：两条快照只证明系统分别收到了不同值。received_at记录应用收到结果的时间，不一定是源页面的观察时间；因此无法确定源数据何时变化，也无法判断变化是否发生在这两个接收时点之间，更不能证明期间没有其他变化。缺少结果、空字段或未提供库存值同样不应自动改写为“缺货”或“价格为零”。

把快照保留为可解释的证据

每条记录尽量带上请求标识、市场、邮编（若指定）、变体、卖家和原始字段值，并分别记录 requested_at、received_at 与明确由接口提供的源时间戳。保留原始价格文本，不要在币种、地区格式和报价含义未确认前，静默转换成可比较的数字。

在写入历史记录前，先验证响应结构和业务必需字段；再把“当前响应字段缺失”“成功返回但结果为空”和“请求或 API 错误”分开。关于响应边界与 received_at 的记录方式，可继续读JSON 响应校验：从响应到商品记录；构建采集流程的其他实践见数据提取高级实践。本页属于Amazon 数据采集 API 完整指南的 API 与数据质量主题。

价格决策前如何评估时间戳证据

API 时间戳能告诉我 Amazon 价格是不是当前价格吗？只有当所选操作明确返回源观察时间戳，并说明其定义时，它才能告诉你源数据何时被观察。客户端的 requested_at 和 received_at 记录应用何时发出请求、收到结果，并不能证明源页面何时被观察。上文链接的商品详情字段文档没有定义逐条记录的源观察时间，因此不要用接收时间代替它。即使有明确的源时间，它也只是一个快照，并不能证明价格此刻仍然有效；还要按你的业务规则判断数据有多旧。

如何判断商品数据接口能否支持我的决策？先将所选操作的文档字段和参数与具体决策逐项对照，再用相同的 ASIN、市场站点、相关变体、卖家情境和请求邮编进行测试；在有代表性的多次请求中比较返回字段，并测量自己的请求到接收耗时。如果决策依赖源时间戳，就确认该操作确实提供了它且定义清楚。这些检查能判断证据是否适合你的流程，但不能保证之后的结账价格与快照相同。

什么时候应该刷新？根据使用旧数据的代价，设定应用可持有数据的最长时间。高影响的价格动作可以要求执行前重新取数并核验关键字段；即便如此，也无法锁定源页面或保证最终价格与库存。如果你正在为 Amazon 商品数据流程比较数据来源，可以查看 Amazon Scraper API，并结合具体操作文档，测试决策所需的字段与时间戳证据。

关键原则：每个价格或库存值都应携带它所描述的商品上下文和本系统的接收时间。若源观察时间没有明确提供，就保留这个未知；让下游决策按自己的风险设定重新查询或停止，而不是把一个快照包装成永久事实。
